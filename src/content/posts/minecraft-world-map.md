这张图来自我们服务器“浦宁三期”的一份网易版基岩存档。目标很简单：不开游戏、不跑服务器，任何人点开网页就能像 Google Earth 一样逛整个城市。做下来比想象中绕，下面按顺序记一下。

## 整体流程

```text
网易基岩版 ZIP
  → 解密 LevelDB（网易加了一层加密）
  → Chunker 转成 Java 1.21 Anvil 世界
  → BlueMap 渲染成 3D 瓦片（自己打了补丁）
  → 补齐内部缺失区块（官方 BDS + 原种子）
  → 前端：中文界面、Google Earth 式操作、夜景灯光
  → Cloudflare 静态托管 + 子域名
```

全程只动工作副本。原始 ZIP 每一步之前都核对 SHA-256，最后一次核对和最初记录一致。

## 1. 解密网易存档

网易版的 `db/` 目录不是标准 LevelDB，直接用工具打开只会得到乱码。写了一个 `decrypt_netease.py`，逐个文件解密，再检查每个 LDB 的 footer 是否完整。最新一版存档有 115 个数据库文件，113 个 LDB 表全部通过检查。

## 2. 基岩版转 Java 版

BlueMap 只认 Java 版世界，所以要用 [Chunker](https://github.com/HiveGamesOSS/Chunker) 的命令行把基岩世界转成 Java 1.21.11 的 Anvil 格式。转换会报一些实体和玩家数据的映射警告，网易的少数专有方块也可能被换成普通方块。这一点到现在也只能说“没发现缺材质”，不能说“全部映射正确”。

## 3. BlueMap 渲染，以及两个补丁

[BlueMap](https://bluemap.bluecolored.de/) 会把世界渲染成按需加载的 3D 瓦片，浏览器里用 WebGL 显示，正好是想要的效果。实际跑起来遇到了几个问题：

- **整张图一片黑。** 转换后的区块没有有效光照数据，渲染出来几乎全黑。打开 `ignore-missing-light-data`，把环境光调高，重新渲染才正常。
- **边界太复杂，渲染太慢。** 存档里只有玩家走过的区域，外轮廓是从区块头里提取的 1,100 条多边形（772 个外轮廓、328 个内洞）。官方的多边形遮罩在这种规模下非常慢，于是在 MIT 许可的 `PolygonMask` 上加了空间网格索引和包围盒裁剪，编了一个本地优化版 JAR。
- **小岛被漏掉。** 后来做覆盖审计时发现有 43 个瓦片没渲染出来：一个小岛完整地落在瓦片内部时，边界线不穿过瓦片边缘，角点也不在岛内，就被误判成“空”。V3 补丁在这种情况下返回“不确定”，交给逐块判断，然后只针对这 43 个瓦片补渲染，没有重跑整个世界。

最终主世界高精度瓦片逐个解压检查，损坏为 0，引用缺失材质为 0。

## 4. 补上地图里的“洞”

存档是玩家实际探索过的区域，城市内部也有不少没加载过的空洞，从上往下看是一块块黑色。补洞的思路是：

1. 从 `level.dat` 读出世界的真实种子，用**官方 Bedrock 专用服务器**、同一个版本、同一个种子生成地形；
2. 只取出“完全被已有区域包围”的内部缺失区块，最后算出来是 3,004 个；
3. 合并到 Java 世界的副本里，**已有区块一个字节都不改**。

中间踩了个坑：服务器的 `tickingarea` 并不等于玩家真正加载区块，很多区块根本不会生成。最后是在一个隔离端口上临时放了一个离线模拟玩家，挨个传送过去让服务器真正生成并保存，跑完就恢复原来的服务器配置。

验收结果：3,004 / 3,004 个区块补齐，原有区块内容变化为 0，清单外新增区块为 0，合并后主世界共 32,290 个区块。

## 5. 前端：像 Google Earth 一样逛

BlueMap 自带的网页能用，但离“随手就能逛”还差一些。在它外面加了一层：

- 中文界面，标题改成“安京人民共和国地图”，最后只保留昼夜和全屏两个按钮；
- 鼠标操作改成 Google Earth 习惯：左键平移、滚轮缩放、中键绕鼠标指向的地形点旋转，用 Playwright 测过旋转支点误差小于 1 像素；
- 手机端单指平移、双指缩放/旋转/俯仰，默认降低高清加载半径；
- 桌面端近景高清半径提到 208 格，远景提到 3900 格，并修了 BlueMap 相机拉远超过 1000 格就卸载全部高清瓦片的问题。

## 6. 夜景灯光

这是最花时间的一部分。因为转换后的世界没有光照数据，夜里整座城是黑的。做法是：

- 从全部区块里把发光方块真实地提取出来（包括基岩版的隐形光源方块），按 128×128 分区存成 JSON，最新一次扫描到约 155 万个光源位置；
- 浏览器按需加载附近光源，按 15 级逐格衰减算出亮度，写回 BlueMap 网格原生的 `blocklight` 顶点属性。不加假灯，也不改存档；
- 远处的低精度层用离线预计算的夜光贴图，让远景城区也能看到灯火。

中途还修过一个很隐蔽的 bug：BlueMap 的法线是有符号 Int8（-128～127），我直接乘了 0.4，采样点被推到几十格外，结果明明旁边就有灯的地面却是黑的。先归一化再偏移之后，同一场景里有光照的顶点从 5.4% 涨到 44.2%。

要说清楚的是：这只是原版**传播距离和等级**的近似，不是游戏的光照引擎。没有做实体方块遮挡，所以封闭房间可能会漏光；动态阴影、真实反射、体积光都没有做。

## 7. 部署

地图前端加数据约一万两千个文件、1.6 GB 左右，单文件最大也就 1 MB 出头。没必要塞进博客的 Git 仓库，所以单独做成一个 Cloudflare 静态站点，挂在子域名 `minecraft.mra-t-g-blog.cn`，博客这边只放介绍和 iframe（也就是这篇文章开头那个）。

几个需要注意的地方：

- BlueMap 开启 `client-decompression`，瓦片以 `.gz` 原样返回，由浏览器端脚本解压，不要再额外加 `Content-Encoding: gzip`，否则会解压两次；
- 关掉实时玩家/标记的轮询，整站纯静态，不需要后端，也不需要一直开着 Minecraft 服务器；
- 稀疏地图会请求不存在的邻近瓦片，网络面板里能看到一些 404，这是正常现象，不是丢数据；
- 每次更新都先在本地预览验收，记下上一个版本号，出问题可以一条命令回滚。

## 还没做完的

- 真机手机性能还没系统测过，不敢说流畅 60 帧；
- 低精度远景在区域边缘会有一些锯齿状的过渡；
- 网易专有方块和原档的逐一比对；
- 真正的阴影和反射，是另一个独立实验了。

总的来说，这个项目最值钱的不是哪一步的技术，而是每一步都留了验收：区块数、瓦片数、哈希、截图都对得上，才往下一步走。做到最后，打开网页看到夜里整座城亮起来，还是挺有成就感的。
