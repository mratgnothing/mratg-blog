今天下午试了一件很有意思的事：让 Codex 通过 Unreal MCP 直接操作虚幻引擎地图。

这和让 Agent 写一段 Unreal Python 脚本不太一样。写脚本时，Codex 只是产出代码，真正执行还要人切回编辑器、粘贴、运行、看结果。接上 MCP 后，编辑器里的能力可以被包装成工具，Codex 能通过工具读关卡、查 Actor、创建对象、修改 transform，再把结果落到当前地图里。

截图里是 `CityPrototype_v02` 关卡。右侧 Outliner 能看到大量 `StaticMeshActor`，视口里是一个城市原型：高层建筑、道路、桥、树、河道和远处的天空盒。这个场景本来就适合测试 Agent 编辑地图，因为它既有明确的空间结构，又不会像完整商业关卡那样复杂到每一次操作都要重新烘焙一堆资源。

## MCP 在这里解决的是什么

传统编辑器自动化有两个问题。

第一个问题是上下文断裂。Agent 不在编辑器里，它不知道当前关卡里有什么，只能靠用户描述。用户说“把桥附近加一点高楼”，但地图里桥在哪里、已有建筑叫什么、坐标范围多大，Agent 都不知道。

第二个问题是执行断裂。Agent 可以写代码，但执行代码、检查视口、修正位置这些动作仍然靠人。一次小改动可能要来回很多轮。

Unreal MCP 的价值就在于把编辑器状态变成 Agent 可以调用的工具上下文。它不需要猜地图，而是可以先问编辑器：当前关卡叫什么、有哪些 Actor、选中了什么、某个对象的位置和类型是什么。然后它再发出编辑操作。

## 我会把它看成三层架构

第一层是 Unreal Editor。地图、Actor、Static Mesh、材质、灯光和保存动作都在这里发生。

第二层是 MCP server。它负责把 Unreal Editor 的能力暴露出来，比如列出关卡对象、读取选中对象、创建 Actor、设置位置、旋转、缩放、保存关卡。

第三层是 Codex。它负责理解人的目标，把“城市中心再高一点”“把道路旁边补树”“选中这组建筑统一调色”翻译成一组可执行工具调用。

这样一来，Codex 的角色不再只是“写 Unreal 工具脚本的人”，而是一个能直接进编辑器干活的关卡助理。

## 一次地图编辑的合理流程

我觉得比较稳的流程是：

1. 先让 Codex 读取当前关卡和 Outliner，确认地图名字、选中对象、Actor 总量。
2. 再让它按类型过滤，比如只看 `StaticMeshActor`、灯光、相机或带特定命名前缀的对象。
3. 如果要改空间布局，先抽样读取几个关键 Actor 的 transform，而不是盲目生成坐标。
4. 创建或修改对象时，一次只做一组有边界的操作，比如“在河道右侧新增 5 个不同高度的盒状建筑”。
5. 操作后再读取结果，必要时让 Codex 调整位置、缩放或命名。
6. 最后保存关卡，或者至少在保存前给出改动清单。

这个顺序的重点是避免 Agent 一次性往地图里塞一大堆不可控对象。虚幻场景不是 Markdown，错误操作的视觉成本很高。小批量、可检查、可回退，才适合长期使用。

## 适合交给 Codex 的地图任务

我现在觉得这类 MCP 工作流特别适合做原型关卡和批量整理。

比如城市白盒阶段，可以让 Codex 按区域生成建筑高度变化，把主干道两侧补齐体块，给桥头加标志性塔楼，或者按“商业区、住宅区、公园区”整理命名和分组。

再比如关卡清理阶段，可以让它检查未命名 Actor、重复命名对象、异常缩放、偏离地图范围的 Actor、材质为空的 Static Mesh。很多事情人工做很烦，但规则明确，Agent 正好适合。

还有一种场景是教学和实验。你可以直接说“把这个关卡改成更像海湾城市的结构”，然后让 Codex 先列计划，再逐步操作：水边道路、桥、码头、塔楼、公园、视线走廊都可以拆成编辑器动作。

## 不适合完全放手的部分

但它还不是“自动做完整 3A 地图”的魔法。

美术判断仍然要人把关。建筑高度节奏、视线焦点、道路尺度、玩家动线、光照氛围，这些不是单靠坐标和 Actor 列表就能判断好的东西。Codex 可以帮忙搭骨架、做批处理、执行明确改动，但最终视觉是否舒服，还是要回到编辑器视口里看。

另外，复杂资产操作也要谨慎。导入资源、替换材质、改蓝图、批量保存包，这些动作对项目影响更大，最好先在测试关卡里验证工具调用，不要直接对主关卡大范围执行。

## 这次实验给我的感觉

这次最大的变化，是 Codex 从“帮我写 Unreal 代码”变成了“帮我动 Unreal 地图”。

以前 Agent 更像一个外部程序员；现在接上 MCP，它开始像坐在编辑器旁边的技术美术助理。它可以读场景状态，可以执行重复编辑，可以按我给的意图调整地图。对于我这种经常在不同 Agent、插件和本地工具之间搭桥的人来说，这条路线很值得继续试。

下一步我会更想把它做成一套固定工作流：先读关卡摘要，再生成改动计划，再小批量编辑，再截图或视口检查，最后保存。只要这条链路稳定下来，Codex 就不只是代码 Agent，而会变成真正能进入内容生产软件里工作的本地操作员。
